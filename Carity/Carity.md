## 1. 개요

### 1-1. 해결하려는 문제

초보 운전자는 다음 세 상황에서 판단이 늦거나 지나치게 긴장합니다.

| 상황 | 운전자가 모르는 것 |
|---|---|
| 좁은 골목 | 왼쪽과 오른쪽에 실제로 몇 cm가 남았는지 |
| 양쪽 주차 구간 | 어느 쪽으로 붙어서 지나가야 하는지 |
| 좁은 길 대향차 | 지나갈 수 있는지, 어디서 멈춰 양보해야 하는지 |

### 1-2. Carity가 하는 일

1. 차량의 속도·기어·조향·브레이크를 받아 3D 골목에서 차를 움직이고, 차체와 장애물 사이 간격을 계산해 경고합니다.
2. 블랙박스 영상을 YOLO로 라벨링해 차량·보행자 위치를 얻고, 이를 도로 위 장애물로 바꿉니다.
3. 지나갈 경로를 계획하고, **규칙 엔진이 행동을 결정**합니다.
4. **AI(Qwen 또는 Claude)는 결정을 바꾸지 않고** 운전자에게 들려줄 문장만 다듬습니다.
5. 결과를 음성과 화면으로 안내하고, 튜토리얼에서 노면 화살표와 "먼저 움직이는 차"로 미리 보여 줍니다.

### 1-3. 설계 원칙

| 원칙 | 이유 |
|---|---|
| 안전 결정은 규칙 엔진이 즉시, 결정론적으로 내림 | 대향차는 2~4초 안에 다가옵니다. LLM은 수백 ms에서 수십 초까지 지연되고, 같은 입력에도 답이 달라질 수 있습니다. |
| AI는 설명과 코칭 문장만 맡음 | "결정은 로직, 설명은 LLM" 구조가 검증과 설명에 유리합니다. AI가 더 위험한 행동을 말하면 무시합니다. |
| "어느 쪽이 가까운가"는 숫자 비교로 판단 | 좌우 여유폭 비교는 숫자 두 개의 비교라 규칙으로 즉시 처리합니다. |
| 거리 계산은 한 곳(`AlleyWorld`)에서만 | 시뮬레이션, 라벨 장면, 튜토리얼, 검증이 같은 거리 엔진을 써서 값이 어긋나지 않습니다. |
| 차선 대신 장애물 안쪽 모서리와 벽을 경계로 씀 | 골목에는 차선이 거의 없습니다. |
| 실제 차량 제어는 하지 않음 | 조명, 매크로, 주행은 시연(가상)입니다. 주행 제한을 우회하지 않습니다. |

### 1-4. 이름 정리 (ver2)

팀 작업 단계마다 쓰던 이름을 **Carity** 하나로 통일했습니다.

| 이전 이름 | 지금 이름 | 비고 |
|---|---|---|
| MOVO, On-sense, Pleos test | **Carity 시뮬레이션** | 앱 이름, 화면 제목, 실내 그림 글자 |
| On-sense 튜토리얼 | **Carity 튜토리얼** | 같은 APK의 별도 런처 아이콘 |
| 가디언즈 라벨 뷰어 (GuardiansViewer) | **Carity 라벨 뷰어** | 앱 이름, 화면 제목 |
| Guardians Labeling Server | **Carity 라벨링 서버** | 서버 첫 화면 제목 |
| Alley Pass | Alley Pass (기능 이름으로 유지) | Carity 시뮬레이션 안의 매크로 기능 |
| 로그 태그 `OnSense*`, `CarTalk*` | `Carity*` | 15-4절 표 |

앱 아이콘은 세 앱 모두 Carity 로고(남색 바탕, 흰색 C, 도로)로 바꿨습니다.

개발용 빌드의 내부 식별자는 바꾸지 않았습니다(`com.example.pleostest`, `com.guardians.viewer`). 바꾸면 실행기 스크립트와 권한 설정도 함께 바꿔야 하기 때문입니다. **제출용 빌드만 패키지 이름을 `com.carity.app`으로 바꿉니다**(11-1절). 그래서 에뮬레이터에는 개발용과 제출용 Carity 시뮬레이션·튜토리얼이 따로 설치됩니다.

### 2-2. 처리 흐름

```
[실시간 시뮬레이션]
차량 속도·기어(AAOS) + 조향·브레이크(Pleos SDK)
  → 3장: 자전거 모델로 가상 차량 이동 → 차체 외곽과 벽·주차차 최소 거리
  → 4장: 근접 경고 · 실내 조명 연출 · 방향 후보 비교 · Alley Pass 매크로

[라벨 장면 판단]
블랙박스 영상 → 5장: YOLO 라벨(프레임별 박스)
  → 6장: 투영해서 장애물·벽 생성 (LabelScene → AlleyWorld), 거리 검증(±2cm)
  → 7장: 경로 계획 CorridorPlanner → CLEAR / YIELD / BLOCKED
  → 8장: 규칙 엔진 AlleyDecisionEngine → 행동·심각도·음성 문장 (최종 결정)
  → 8장: AI 다듬기 AiJudge(Claude 또는 Qwen) → AiJudge.merge (덜 조심스러운 답 거부)
  → 9장: 음성 Pleos TTS → Android TTS → PC 음성
  → 10장: 시뮬레이션 탭 / 튜토리얼
```

## 3. 차량 상태 연동과 3D 골목 시뮬레이션

구현: `MainActivity.kt`, `AlleyPassSimulationView.kt`, `AlleyWorld.kt`, `Alley3dView.kt`, `Alley3dRenderer.java`

### 3-1. 차량 상태 수신

| 값 | 경로 | 구현 |
|---|---|---|
| 속도 | AAOS Car API (`CAR_SPEED` 권한) | `VehicleSpeedTest` |
| 기어 P/R/N/D | AAOS Car API | `VehicleGearSource` |
| 조향 | Pleos Vehicle SDK | `PleosSteeringSource`, `PleosSteeringMapping` (원본 각도 → -1~1) |
| 브레이크 | Pleos Vehicle SDK | `PleosBrakeTest` |
| 주행 제한(UX) | AAOS UX Restrictions | `DrivingUxSource` |
| 위치 | Pleos 위치 | `PleosLocationProbe` (진단용, 외부 전송 없음) |

- 받은 값은 앱 안의 상태로 모으고, 일정 시간 새 값이 없으면 "미수신"으로 처리합니다. 오래된 입력으로는 차를 움직이지 않습니다.
- 오른쪽 정보 패널(`VehicleInfoPanel`)에 속도, 조향 방향과 값, 브레이크, 기어를 표시합니다.
- 단위: 속도 입력 m/s, 화면 km/h, 위치·간격 m, 방향은 라디안입니다.

### 3-2. 차량 이동 계산 (단순화한 자전거 모델)

1. 조향값을 정규화(-1~1)한 뒤 최대 조향각으로 바꿉니다.
2. 매 프레임(50 ms) 방향(heading)을 먼저 갱신하고, 그 방향으로 위치를 옮깁니다.
3. 빠르게 움직일 때 장애물을 건너뛰지 않도록 이동 구간을 여러 번 나눠 계산합니다.
4. R 기어에서는 속도 부호를 뒤집어 후진합니다(`VehicleMotionInput.signedSpeed`, 이미 음수면 다시 뒤집지 않음).

### 3-3. 거리 계산

- 차량을 중심 기준 직사각형(1.8 × 4.2 m)으로 보고, 회전하면 네 모서리 좌표를 다시 계산합니다.
- 벽, 주차 차량, 안전봉을 모두 다각형으로 보고 다음 순서로 계산합니다.
  1. **분리축 정리(SAT)** 로 충돌 여부를 판단합니다.
  2. 충돌하지 않으면 **선분 사이 최소 거리**로 실제 여유를 구합니다.
- 중심점 거리가 아니라 **차체 외곽끼리의 최소 거리**를 씁니다. 운전자에게 중요한 것은 실제 차체 옆면의 여유이기 때문입니다.
- 결과: 좌·우·앞·뒤 방향별 최소 거리, 접촉 여부, 가장 가까운 장애물.

### 3-4. 3D 골목

| 요소 | 내용 |
|---|---|
| 렌더링 | OpenGL ES, GL 스레드에 불변 스냅샷(`Alley3dFrame`)으로 전달 |
| 기본 골목 | 양쪽 벽, 주차 차량, 도로 끝 y = 100 m (전진 종료 위치 97.5 m) |
| 중앙선 안전봉 | x = 0 위에 y = 76.5 ~ 92.5 m, 4 m 간격 5개. 높이 0.95 m, 받침 0.45 m. 양옆으로 지나갈 수 있음 |
| 접촉 | 빨간 표시와 함께 가상 이동을 멈춤 |
| 라벨 장면 | 6장에서 만든 벽·장애물·도로 끝으로 바뀜 |

### 3-5. 입력 방식

| 버튼 | 동작 | 실제 차량 값 변경 |
|---|---|---|
| 3D 자동 시연 | 기본 골목은 10초 가상 시나리오, 라벨 장면은 경로 계획을 따라 주행 | 없음 |
| SDK 연동 시작 | 실제 SDK 속도·조향으로 가상 차를 움직임 | 없음 (읽기만) |
| 가상 키보드 시연 | 실제 P·0km/h 확인 후, 앱 안에서만 쓰는 가상 기어와 키 입력(↑/W 가속, ↓/S 브레이크, ←/A·→/D 조향, Space 정지) | 없음 |
| Console 키보드 연결 | Pleos Virtual Console(에뮬레이터 `127.0.0.1:8088`)에 연결해 실제 기어·속도·조향 요청 | 있음 (에뮬레이터만) |
| 3D 초기화 | 위치·시연·매크로를 초기화하고 Console 제어 중지 | 정차·P 복귀 |

- Console 연결은 P·0km/h에서 시작합니다. 화면을 벗어나거나 포커스를 잃으면 입력을 정리하고 정차·P로 되돌립니다.
- 실제 R 기어로 바꾸면 Pleos 후방카메라 화면이 앞에 뜹니다. 이를 끄거나 우회하지 않습니다.

## 4. 근접 경고 · 실내 조명 · Alley Pass 매크로

### 4-1. 근접 경고 단계

| 조건 | 표시 | 안내 |
|---|---|---|
| 접촉 | 빨강, 이동 정지 | 즉시 정차 |
| 0.3 m 이하 | 빨강 (진입 시 기준선 3회 점멸) | 정차 후 확인 |
| 0.8 m 이하 | 주황 | 공간 주의 |
| 1.2 m 이하이면서 가까워지는 중 | — | 접근 경고 (이전 프레임 거리와 비교) |
| 속도 10 km/h 초과 | — | 속도 줄이기 |
| 그 밖 | 초록 | 일반 안내 |
| 입력 미확인 | 회색 | — |

구현: `SideClearanceWarning.level`, `AlleyPassDistances`

### 4-2. 방향 후보 비교

- 현재 속도로 좌·직진·우 세 가지 가상 조향 경로를 약 2.5초 앞까지 그려 보고, 경로마다 최소 여유를 계산합니다(`AlleyWorld.guidance`).
- 좌/우가 직진보다 넓으면 그쪽을 안내하고, 셋 다 좁으면 정차와 공간 확인을 먼저 안내합니다.
- 실제 조향 명령이 아니라 참고 안내입니다.

### 4-3. 실내 조명 연출

| 항목 | 내용 |
|---|---|
| 구간 | 좌우 각각 16구간, 기본은 모두 초록 |
| 가까워질 때 | 도어 → 중앙 방향으로 경고색 구간이 늘어남 |
| 멀어질 때 | 중앙 → 도어 순서로 초록 복귀. 1.6 m 이상이면 전체 초록 |
| 점멸 | 빨강 진입 시 기준선 500 ms 주기 3회 점멸 후 고정 (같은 빨강 구간에서 반복 안 함) |
| 진행 시간 | 전체 길이 1800 ms, 프레임 최대 64 ms |
| 실제 조명 API | `AmbientLightBridge`: 지원 영역 확인 → 원래 값 저장 → SET → 독립 GET 재조회 → 종료 시 복원 |

화면의 16구간은 연출입니다. 차량 하드웨어 16영역을 제어하는 것이 아닙니다. 에뮬레이터에서 SET 응답은 왔지만 재조회 값이 흰색이라 실제 색 적용은 **미확인**입니다.

### 4-4. Alley Pass 매크로 (가상 실행)

좁은 곳에서 운전자가 긴장해 브레이크를 여러 번 밟는 상황을 발동 조건으로 잡았습니다.

| 단계 | 조건 / 동작 |
|---|---|
| 감지 | 0~10 km/h 저속 + 주변 1.2 m 이하 + 15초 안에 브레이크 해제→누름 3회 |
| 확인 | 실제 정차와 P단을 다시 확인 |
| 사용자 동의 | 확인창에서 "가상 실행"을 눌러야 시작 |
| 실행 | 미러 접기 → 조수석 창문 → 비상등 3회 점멸 → 완료 (화면 카드로 표시) |
| 안전 | 단계마다 토큰과 정차 조건을 다시 확인, 조건이 깨지면 취소 |

구현: `AlleyMacroGate`, `AlleyMacroPresentation`, `AlleyPassSimulationView.executeMacro`

공개 SDK에서 일부 제어가 확인되지 않아 매크로는 **가상 실행**입니다. 실제 액추에이터를 움직이지 않습니다.

## 6. 라벨 → 장애물 변환과 거리 계산

구현: `LabelScenario.kt` (`DashCamera`, `LabelSceneBuilder`), `LabelDistanceCheck.kt`

### 6-1. 카메라 가정 (캘리브레이션 전)

| 값 | 기호 | 설정 | 근거 |
|---|---|---|---|
| 지평선 위치 | h | 화면 높이의 0.53 | 도로 소실점 육안 추정 |
| 초점거리/화면폭 | f | 0.384 | 수평 화각 약 105° 가정 |
| 카메라 높이 | H | 1.30 m | 가정 |
| 보닛 끝 | — | 화면 높이의 0.82 | 프레임 육안 확인 |
| 화면비 | a | 16:9 | — |

### 6-2. 투영 식 (평지 핀홀 근사)

```
전방거리  Z = H · f · a / (y₂ − h)          (y₂ ≤ h 이면 지평선 위 → 버림)
좌우위치  X = (x − 0.5) · Z / f             (왼쪽이 음수)
```

- 보닛에 잘린 박스(y₂ ≥ 0.81)는 실제보다 가깝게 계산되므로, 보닛 끝이 보이는 최소거리(약 3.1 m)로 둡니다.
- 박스의 **안쪽 모서리**(왼쪽 객체는 x₂, 오른쪽 객체는 x₁)가 자차와의 간격을 정합니다.
- 객체 크기는 종류별 기본값을 씁니다: 승용차 1.8×4.4 m, 트럭 2.0×6.0 m, 버스 2.3×9.0 m, 보행자 0.6×0.6 m, 자전거 0.6×1.7 m, 오토바이 0.8×2.0 m.

### 6-3. 걸러내는 박스

| 조건 | 처리 | 이유 |
|---|---|---|
| 신뢰도 < 0.4 | 버림 | 오검출 |
| 보닛에 잘림 + 신뢰도 < 0.5 | 버림 | 보닛 반사 오검출이 많음 |
| 폭 > 화면 80%, 또는 화면 대부분을 덮음 | 버림 | 자차 보닛·벽을 차로 오검출 |
| 전방 32 m 초과, 좌우 7 m 초과 | 버림 | 거리 오차가 큼 |
| 같은 위치 겹친 박스(car/truck 중복) | 신뢰도 높은 것 하나 | 중복 검출 |

### 6-4. 객체 역할

| 역할 | 판정 기준 | 장애물 처리 |
|---|---|---|
| 측면 장애물 | 진행 폭(±1.1 m)에 0.3 m 미만 걸침 | 안쪽 모서리를 기준으로 배치 |
| 경로상 장애물 | 진행 폭에 0.3 m 이상 걸침 | 보이는 범위 전체를 막힌 것으로 (대각선 차량은 길이 포함, 최대 차폭 + 1 m) |
| **대향차** | 경로상 + 차량 + **1초 전 대비 박스 높이 증가율 ≥ max(1.08, 측면 정지물체 증가율 × 1.1)** | 경로 계획에서 두 차가 만나는 지점부터 차로를 차지 |

위치만으로 대향차를 판단하면 경로에 걸친 주차차를 대향차로 오판합니다(5-3절 v1의 실패 원인). 그래서 "정지한 측면 물체보다 뚜렷하게 빨리 커지는 경로상 차량"만 대향차로 봅니다.

### 6-5. 장면(세계) 구성

| 항목 | 값 |
|---|---|
| 자차 출발 위치 | y = 4 m, x = 0 (차체 1.8 × 4.2 m) |
| 접근 구간 | 장면 전체를 6 m 앞으로 밀어서 판단 시점 전에 출발 |
| 카메라 위치 | 차량 중심보다 0.6 m 앞 |
| 벽(골목 경계) | 좌우 각각 max(2.4 m, 가장 바깥 객체 + 0.3 m) |
| 도로 끝 | max(30 m, 가장 먼 객체 + 10 m) |

> 벽과 연석은 YOLO가 검출하지 않아 객체 바깥쪽을 경계로 추정합니다. 실제 벽보다 넓게 잡힐 수 있습니다(13장).

### 6-6. 거리 계산 검증

라벨로 만든 장면의 거리가 올바로 계산되는지 객체마다 확인합니다.

- **기대값**: 투영 좌표로 직접 계산한 "차체 옆면 ↔ 객체 안쪽 모서리" 거리
- **측정값**: 그 객체 하나만 둔 `AlleyWorld`에서 자차를 곧게 통과시키며 `clearance()`로 잰 최소 간격
- 경로상 객체는 자차를 반대쪽으로 0.5 m 비켜 통과시켜 잽니다.
- **허용 오차 2 cm**. 화면에 `거리 검증 n/n 일치`와 객체별 기대/측정값을 표시합니다.

## 7. 경로 계획

구현: `CorridorPlanner.kt`

### 7-1. 방법

1. 출발점부터 도로 끝까지 **0.5 m 간격 단면**을 만듭니다.
2. 단면마다 차량 중심이 갈 수 있는 x 구간을 구합니다. 차체 반폭 0.9 m와 여유 0.25 m를 더해 장애물과 벽을 뺍니다.
3. 구간 안에서 목표 x를 고릅니다. 폭이 1 m보다 좁으면 가운데로 가고, 넓으면 현재 위치를 유지하되 장애물에서 0.3 m 더 떨어집니다.
4. **조향 한계**: 0.5 m 진행에 횡이동 0.15 m(기울기 0.3)까지만 허용합니다. 뒤에서 앞으로 한 번 다듬어 필요한 횡이동을 미리 시작하고, 앞에서 뒤로 한 번 다듬어 출발점과 잇습니다.
5. **차체 회전 보정**: 횡이동 중에는 차체가 틀어져 모서리가 장애물에 가까워집니다. 회전을 반영한 간격이 0.35 m보다 작으면 두 가지를 시도합니다. 하나는 반대쪽으로 밀어내는 것이고, 다른 하나는 횡이동을 더 완만하게(진입은 일찍, 이탈은 늦게) 바꾸는 것입니다. 통과할 수 있으면서 최소 간격이 가장 큰 경로를 고릅니다.

### 7-2. 결과

| 결과 | 조건 | 경로 |
|---|---|---|
| `CLEAR` | 모든 단면을 통과 | 도로 끝까지 |
| `YIELD` | 대향차가 있고, 옆으로 비켜 설 곳이 있음 | **오른쪽 우선**(우측통행). 대향차 2 m 앞까지 중 가장 앞쪽 정차점. 대향차가 지나갈 폭(차폭 + 양쪽 0.3 m)이 남아야 함 |
| `BLOCKED` | 지나갈 수 없음 | 막힌 지점 1.5 m 앞에서 정차 |

대향차는 처음부터 차로를 막는 것으로 보지 않습니다. **두 차가 만나는 지점**(현재 간격의 절반)에서 차체 길이와 1 m를 뺀 지점부터 막습니다.

### 7-3. 출력

경로 점마다 `x, y, 진행 방향, 좌·우 간격, 최소 간격`을 담고, 경로 전체의 `최소 좌/우 간격`, `가장 좁은 점`, `정차 지점`, `설명 문구`를 함께 돌려줍니다.

## 8. 판단 — 규칙 엔진과 AI(Qwen/Claude)

### 8-1. 상황 판별 설계 (참고: 1차 설계안)

1차 설계안의 상태머신입니다. 현재 구현은 이 상태를 경로 계획 결과(CLEAR/YIELD/BLOCKED)와 규칙 순서로 대신합니다.

| 전이 | 조건 |
|---|---|
| NORMAL → NARROW | 도로폭 < 자차폭 × 2 + 1.0 m (약 4.7 m) |
| NARROW → ONCOMING | 대향차 존재 + 충돌까지 시간(TTC) < 4초 |
| ONCOMING → BLOCKED | 도로폭 < 자차폭 + 대향차폭(1.8 m) + 여유 0.6 m |

### 8-2. 역할 분담

| 구분 | 규칙 엔진 (`AlleyDecisionEngine`) | AI (`AiJudge`) |
|---|---|---|
| 하는 일 | 행동 결정, 심각도, 기본 음성 문장 | 음성 문장 다듬기, 판단 근거 문장 |
| 응답 시간 | 즉시 (밀리초) | Qwen 약 12초 (PC 측정), Claude 수 초 |
| 결정 권한 | **최종** | 없음 (더 위험한 행동을 말하면 무시) |
| 실패 시 | — | 규칙 문장으로 자동 대체 |

### 8-3. 행동 종류

| 행동 | 한국어 표시 | 위험도 순위 | 의미 |
|---|---|---|---|
| `PROCEED` | 천천히 진행 | 0 | 여유 충분 |
| `KEEP_LEFT` / `KEEP_RIGHT` | 왼쪽/오른쪽으로 조정 | 1 | 한쪽이 가까움 |
| `SLOW` | 감속 | 2 | 좁은 구간, 과속, 앞에서 막힘 |
| `YIELD_RIGHT` / `YIELD_LEFT` | 오른쪽/왼쪽 정차·양보 | 3 | 대향차를 먼저 보냄 |
| `STOP` | 정차 | 4 | 초근접, 접촉, 통과 불가 |
| `REVERSE` | 정차 후 후진 | 4 | 대향차 + 비켜설 곳 없음 |

심각도: 0 안내 · 1 주의 · 2 경고 · 3 긴급

### 8-4. 판단 규칙 (위에서부터 처음 맞는 규칙 하나를 적용)

| 순서 | 조건 | 행동 | 심각도 | 음성 문장 예 |
|---|---|---|---|---|
| 1 | 차체 접촉 | STOP | 3 | "접촉했습니다. 즉시 정차하고 주변을 확인하세요." |
| 2 | 최근접 ≤ 0.3 m (앞) | STOP | 3 | "앞이 25센티미터로 너무 가깝습니다. 정차하세요." |
| 2 | 최근접 ≤ 0.3 m (옆) | STOP | 3 | "왼쪽에 너무 가깝게 붙었습니다. 정차 후 핸들을 오른쪽으로 돌려 천천히 빠져나오세요." |
| 3 | 경로 YIELD + 대향차 40 m 이내 | YIELD_RIGHT/LEFT | 2 | "앞에서 차가 옵니다. 오른쪽 빈 곳에 붙어 정차하고 먼저 보내세요." |
| 4 | 경로 BLOCKED + 정차점까지 < 8 m | REVERSE(대향차 있음) / STOP | 2 | "비켜설 공간이 없습니다. 정차 후 천천히 후진해 넓은 곳에서 양보하세요." |
| 5 | 경로 BLOCKED + 정차점까지 < 25 m | SLOW | 1 | "앞쪽 길이 좁아 지나가기 어렵습니다. 속도를 줄이고 정차를 준비하세요." |
| 6 | 속도 > 10 km/h + 최근접 < 1.2 m | SLOW | 2 | "좁은 길입니다. 시속 10킬로미터 이하로 천천히 가세요." |
| 7 | 최근접 < 0.6 m + 좌우 차이 > 0.3 m | KEEP_반대쪽 | 1 | "왼쪽에 가깝습니다. 40센티미터입니다. 핸들을 오른쪽으로 살짝 돌리세요." |
| 8 | 좌우 모두 < 0.6 m | SLOW | 1 | "양쪽이 모두 좁습니다. 가운데를 유지하며 천천히 지나가세요." |
| 9 | 앞 12 m 안 경로 최소 간격 < 0.5 m | SLOW | 1 | "앞에 좁은 구간이 있습니다. 왼쪽 간격이 35센티미터까지 줄어드니 천천히 가세요." |
| 10 | 위 조건 없음 | PROCEED | 0 | "좌우 여유가 충분합니다. 천천히 진행하세요." |

- 0.3 m / 0.8 m는 4-1절 경고 등급(빨강/주황)과 같습니다. 0.6 m는 "핸들 조정 권고" 기준입니다.
- 음성 거리는 읽기 쉽게 바꿉니다. 1 m 미만은 5 cm 단위("35센티미터"), 1 m 이상은 "1.2미터"입니다.
- 같은 안내를 반복하지 않도록 판단마다 **상황 키**(행동 + 방향)를 둡니다.

> **팀 검토 필요**: 1차 설계안은 "후진 유도는 초보자에게 위험하므로 제외"였습니다. 현재 구현은 대향차가 있고 비켜설 곳이 전혀 없을 때만 `REVERSE`를 안내합니다. 제외하려면 규칙 4의 행동을 `STOP`으로 바꾸면 됩니다.

### 8-5. AI 판단 (Qwen / Claude)

#### 제공자 선택

| 조건 | 사용 모델 | 호출 방식 |
|---|---|---|
| `.env`에 `ANTHROPIC_API_KEY` 있음 | Claude (`claude-haiku-5-5`) | Messages API, `max_tokens 300` |
| 키 없음 (기본) | Qwen (`qwen2.5:3b`, PC의 Ollama) | OpenAI 호환 `/v1/chat/completions`, `temperature 0.2`, `max_tokens 150` |

- 연결 제한시간 4초, 응답 제한시간은 Qwen 45초(PC CPU에서 첫 응답이 15초를 넘는 경우가 있어 늘림), Claude 20초입니다.
- 실행기가 시작할 때 Qwen 모델을 미리 메모리에 올려 60분 유지합니다(`keep_alive 60m`). 첫 호출 지연을 줄이기 위해서입니다.
- 키는 빌드할 때 APK에 들어가므로 외부 배포 빌드에는 넣지 않습니다.

#### 입력 (원본 영상이 아니라 정리된 측정값과 규칙 결과)

```json
{
  "measurements": {
    "left_m": "0.42", "right_m": "1.10", "front_m": "6.30",
    "nearest_obstacle": "왼쪽 주차 차량", "speed_kmh": "8.0",
    "road_width_m": "5.20", "oncoming_ahead_m": "none",
    "plan": "CLEAR:끝까지 통과 가능", "plan_min_left_m": "0.35", "plan_min_right_m": "0.41",
    "scene": "왼쪽 1개 · 오른쪽 0개 · 대향 0개 · 경로상 1개 · 도로폭 5.2m"
  },
  "rule": {
    "action": "KEEP_RIGHT", "severity": 1,
    "headline": "왼쪽 40센티미터 · 오른쪽으로",
    "speech": "왼쪽에 가깝습니다. 40센티미터입니다. 핸들을 오른쪽으로 살짝 돌리세요.",
    "reasons": ["왼쪽 0.42m, 오른쪽 1.10m"]
  }
}
```

#### 지시문(프롬프트) 요약

1. 안전 판단은 `rule.action`이 최종입니다. 규칙보다 덜 조심스러운 행동(진행, 가속)을 권하지 않습니다.
2. `speech`는 TTS가 바로 읽을 한국어 존댓말 한 문장, 45자 이내입니다. 순서는 **어느 쪽 → 얼마나 가까운지 → 무엇을 할지**입니다.
3. 영어, 기호, 괄호, 이모지, 소수점 숫자를 쓰지 않고, 거리는 "30센티미터", "1.2미터"처럼 읽는 말로 씁니다.
4. `action`은 정해진 8개 중 하나만 씁니다.
5. 출력은 JSON 하나입니다: `{"action": "...", "speech": "...", "reason": "..."}`

#### 응답 처리

1. `<think>` 블록과 코드펜스를 지우고, 첫 `{`부터 마지막 `}`까지를 JSON으로 읽습니다.
2. 음성 문장에서 괄호와 기호를 지우고 80자로 자릅니다.
3. **결합 규칙** (`AiJudge.merge`):

| 경우 | 최종 행동 | 읽을 문장 | 출처 표시 |
|---|---|---|---|
| AI 실패·응답 없음 | 규칙 | 규칙 문장 | 규칙 엔진 |
| 규칙 심각도 3(긴급) | 규칙 | 규칙 문장 | 규칙 엔진(긴급) |
| AI 행동이 규칙보다 덜 위험 | 규칙 | 규칙 문장 | 규칙 엔진(AI 완화 거부) |
| 그 밖 | 규칙 | **AI 문장** | Claude 또는 Qwen |

#### 호출 시점

- 상황 키가 바뀌고 0.4초 동안 유지되면 1회 호출합니다. 깜빡이는 상황에서는 호출하지 않습니다.
- 새 요청이 들어오면 이전 결과는 버립니다(`AiCoordinator`).
- 장면을 처음 적용했을 때(정차 상태)에도 1회 호출해 장면 판단을 읽어 줍니다.

### 8-6. 장면 안내 문장 (튜토리얼·장면 적용 시)

`SceneAnalysis`가 장면과 경로에서 만듭니다. AI 없이도 동작합니다.

| 문장 | 생성 규칙 | 예 |
|---|---|---|
| 상황 설명 | 도로폭 + 좌/우/가운데 장애물 수 + 대향차 여부 | "길 폭은 5.2미터입니다. 왼쪽에 한 개, 길 가운데에 한 개 장애물이 있습니다." |
| 경로 안내 | 경로가 출발점에서 0.3 m 넘게 움직인 방향 + 가장 좁은 곳 + 결과 | "노면 화살표를 따라 왼쪽으로 붙어서 천천히 가세요. 가장 좁은 곳은 오른쪽 35센티미터입니다. 끝까지 지나갈 수 있습니다." |
| 마무리 | 결과별 고정 문장 + 최소 간격 | "잘 지나갔습니다. 가장 가까웠던 간격은 왼쪽 35센티미터, 오른쪽 40센티미터입니다." |

## 10. 화면 기능 — 시뮬레이션 · 튜토리얼 · 라벨 뷰어

### 10-1. Carity 시뮬레이션

왼쪽 3D 골목, 오른쪽 패널(50:50) 구성입니다. 오른쪽 패널에는 탭이 두 개 있습니다.

| 탭 | 내용 |
|---|---|
| `[실내 조명]` | 차량 실내 그림 + 좌우 16구간 조명 연출(4-3절), 실제 조명 스위치 |
| `[라벨 장애물·AI 판단]` | 아래 표 |

| 영역 | 내용 |
|---|---|
| 장면 선택 | 기본 골목 · 합성 대향차 연습 · 앱 내장 라벨 6개 · **PC 라벨 불러오기**(서버 폴더 탐색 → 판단이 필요한 순간 자동 추천) |
| 장면 | 객체별 종류, 위치(왼쪽/오른쪽/가운데), 전방거리, 안쪽 모서리 |
| 거리 계산 검증 | `n/n 일치`와 객체별 기대/측정값 |
| 경로 계획 | 결과, 최소 좌/우 간격, 정차 지점, 실시간 좌·우·앞 간격 |
| 규칙 엔진 판단 | 행동, 근거, 음성 문장 (심각도별 색) |
| AI 판단 | 제공자, 응답 시간, AI 권고, 최종 음성 문장, 재생 출처 |
| 버튼 | 판단 음성 듣기 · AI 다시 판단 · 튜토리얼로 보기 · 기본 골목으로 |

- 장면을 고르면 3D 골목의 벽과 장애물이 라벨 기준으로 바뀝니다.
- **3D 자동 시연**은 라벨 장면에서 경로를 따라 달립니다. 기본 2.5 m/s이고, 앞 4 m 안에 0.5 m보다 좁은 곳이 있으면 1.2 m/s로 줄이며, 정차점에서 멈춥니다.
- 주행 중에는 1초마다 현재 위치에서 경로를 다시 계획해 판단에 씁니다.
- 하단 버튼(3-5절)과 기어 버튼 D/R/N/P, 진단 정보 펼침/접기가 있습니다.

### 10-2. Carity 튜토리얼 (별도 런처 아이콘)

같은 APK 안의 별도 아이콘(`TutorialActivity`)입니다. 위에서 내려다본 디지털 트윈 화면(`TutorialView`)과 오른쪽 안내 패널로 구성합니다.

| 단계 | 화면 | 음성 | 다음 단계 조건 |
|---|---|---|---|
| 1 상황 파악 | 장애물 강조(깜빡임), 카메라가 앞쪽 장애물까지 훑고 돌아옴 | 상황 설명 문장 | 6.5초 |
| 2 AI 판단 | 규칙 판단 카드 → AI 결과 카드 | 최종 음성 문장 (AI가 3.5초 안에 답하지 않으면 규칙 문장 먼저) | AI 결과 후 4.5초, 최대 14초 |
| 3 노면 방향 표시 | 자차 폭 띠 + 흐르는 화살표(쉐브론)가 3초 동안 경로를 따라 펼쳐짐, 정차선 | 경로 안내 문장 | 7초 |
| 4 미리 보기 | 반투명 "고스트 차"가 경로를 4 m/s로 먼저 주행 | "투명한 차가 먼저 지나가는 길을 보여 드릴게요." | 고스트 도착 + 마무리 동작 |
| 5 따라 주행 | 자차가 2 m/s로 주행(좁은 곳은 절반 속도), 좌우 간격선과 수치, 판단 카드 | 상황이 바뀔 때마다 규칙 문장 | 도착 + 마무리 동작 |
| 6 정리 | 결과와 최소 간격 카드 | 마무리 문장 | (처음부터 버튼) |

결과별 마무리 동작 (4·5단계):

| 결과 | 동작 |
|---|---|
| CLEAR | 끝 지점 도착 후 0.6초 뒤 다음 단계 |
| YIELD | 정차("여기서 정차하고 마주 오는 차를 먼저 보내세요.") → 대향차가 자차 옆 빈 차로로 5 m/s로 지나감 → 1초 |
| BLOCKED (대향차 없음) | 정차선 앞 정차("앞이 차 폭보다 좁습니다.") → 2.5초 |
| BLOCKED (대향차 있음) | 후진 화살표 + 5 m를 1.2 m/s로 후진 시연 |

화면 요소: 승용차 파랑, 트럭·버스 보라, 경로상 객체 주황, 보행자 원, **대향차 빨강 + 아래쪽 화살표**, 경로는 청록 띠와 쉐브론, 정차선은 양보 주황·정차 빨강, 간격 표시는 0.3 m 이하 빨강·0.8 m 이하 주황·그 밖 청록입니다.

조작 버튼: 장면 선택, 처음부터, 일시정지/계속, 다음 단계, 음성 켬/끔. 시뮬레이션 탭의 "튜토리얼로 보기"로 같은 장면을 바로 열 수 있습니다.

### 10-3. Carity 라벨 뷰어

태블릿(에뮬레이터)에서 PC 폴더의 영상과 이미지를 열고, 라벨된 파일은 박스와 함께 재생합니다.

```
[라벨 뷰어]                          [라벨링 서버]
 폴더 목록 ── /api/files ──────────► 파일 나열 + 라벨 여부
 파일 선택 ── /api/prepare ────────► 필요한 작업만 등록 (변환 · YOLO 라벨링)
   (로딩 화면, 0.7초마다 진행률) ◄── /api/jobs/{id}
 재생 ◄────── /api/labels, /api/media
   └ 박스 오버레이 (추적 ID 기준으로 프레임 사이 보간, vsync 동기)
```

| 기능 | 내용 |
|---|---|
| 연결 | 서버 주소 입력란 + 연결 버튼. 에뮬레이터 `http://10.0.2.2:8765`, 실제 태블릿 `http://<PC IP>:8765`. 주소 앞에 붙은 기호나 공백은 자동으로 정리 |
| 탐색 | 폴더 이동, 라벨됨/미라벨 필터·배지, 기기 파일 업로드 |
| 재생 | 승용/트럭·버스/사람/이륜 색 구분 박스, 라벨, 차선(중앙선 노랑) |

| 파일 | 역할 |
|---|---|
| `ui/MainActivity.kt` | 서버 연결, YOLO 백엔드 표시, PC 폴더 탐색, 필터, 업로드 |

| `net/ServerApi.kt` | HTTP 클라이언트(외부 라이브러리 없음), 주소 정리 |

## 11. 통합 실행기

구현: `Carity.bat`(더블클릭 진입점) → `carity.ps1`(본체). 실행 기록은 `logs/carity.log`에 남습니다.

| 메뉴 | 명령 | 하는 일 |
|---|---|---|
| 1 | `start` | Ollama 시작·Qwen 미리 적재 → 라벨링 서버 → 에뮬레이터 → (앱이 없으면) 빌드·설치 → 권한 미리 허용 → 화면 점검 → 상태 |
| 2 | `setup` | 처음 1회: 서버 Python 환경, Ollama + qwen2.5:3b, `.env` |
| 3 | `build` | 두 앱 빌드(`:app`, `:viewer`) 후 에뮬레이터에 설치 |
| 4 | `server` | 라벨링 서버만 실행 |
| 5 | `status` | 서버(데이터 폴더·YOLO 모델), 포트 사용 프로세스, 데이터 개수, 에뮬레이터→PC 접속, Ollama, 에뮬레이터, 앱 설치, 현재 화면 |
| 6 | `logs` | 앱 로그를 `logs/app_날짜.txt`로 저장. Carity 태그, 앱 실행·강제 종료(`FATAL`, `Force finishing`, `has died`), 권한 오류, 주행 제한 기록까지 모음 |
| 7 | `copydata` | 영상·라벨을 `data/`로 복사 |
| 8 | `stopall` | 서버·서버 창·복사 작업·Gradle/Kotlin 데몬·adb 종료 (폴더 이름 변경 전에 사용) |
| 9 | `diag` | 서버와 에뮬레이터를 켠 뒤 네트워크 진단 (경로, 프록시, 8765·11434 접속, 앱 로그) |
| 10 | `reset` | 에뮬레이터를 끄고 **저장된 상태 없이 처음부터 부팅**, 앱 최신 빌드로 재설치, 권한 허용. 버튼이 눌리지 않을 때 사용 |
| 11 | `releasekey` | 제출용 서명 키(`release\carity-release.jks`) 생성, `.env`에 서명 정보 기록 |
| 12 | `release` | 제출용 APK 빌드 → `release\Carity-버전.apk`, 서명 확인(apksigner), SHA-256 기록, 에뮬레이터 설치(선택) |
| 13 | `shot` | 에뮬레이터 화면을 스토어 스크린샷 PNG로 저장 |

동작 세부:

- **서버 데이터 폴더 확인**: 이미 실행 중인 서버의 데이터 폴더가 `.env`의 `DATA_ROOT`와 다르면 재시작합니다.
- **서버 Python 환경**: `server/labeling_server/.venv`가 없고 `LEGACY_SERVER`(기존 설치)의 환경이 있으면 복사하지 않고 그대로 씁니다. 둘 다 없으면 `setup`이 새로 설치합니다(PyTorch CUDA 12.8 + requirements).
- **에뮬레이터**: 이미 켜져 있는데 adb가 못 찾으면 두 번째 실행 대신 adb를 다시 시작합니다.
- **콜드 부트 (기본)**: `.env`의 `EMULATOR_COLD_BOOT=true`면 저장된 상태(스냅샷) 없이 처음부터 부팅합니다(1~3분). 한 PC에서 스냅샷으로 빠르게 부팅(약 10초)하면 화면은 보이지만 터치가 먹지 않고 1분쯤 뒤 에뮬레이터가 꺼지는 현상이 있었습니다. 콜드 부트로는 재현되지 않아 기본값으로 바꿨습니다.
- **권한 미리 허용**: `CAR_SPEED`, `TTS_SERVICE`, `FUSED_LOCATION`을 현재 사용자(보통 user 10)에게 허용합니다. 보이지 않는 권한 창이 앱 화면을 가리는 문제를 막습니다.
- **화면 점검**: 권한 창이나 "응답 없음" 창이 맨 위에 있으면 경고하고 뒤로가기를 보냅니다.

### 11-1. 제출용(release) 빌드

Pleos App Market 제출 가이드와 심사 기준(외부 서버 의존 금지, 권한 최소화, 시험 기능 제외)에 맞춰 release 빌드를 debug와 다르게 구성합니다. 기능 스위치는 `CarityFeatures.kt`, 권한 제거는 `src/release/AndroidManifest.xml`에 있습니다.

| 항목 | debug | release |
|---|---|---|
| 패키지 | `com.example.pleostest` | `RELEASE_APP_ID` (기본 `com.carity.app`) |
| AI | Qwen/Claude | 사용 안 함 (`AiJudge.Provider.NONE`, 규칙 엔진 문장) |
| PC 라벨·PC 음성 | 사용 | 사용 안 함 |
| 위치·창문·미러·조명 권한 | 선언 | 제거 |
| 개발용 버튼 (Console·가상 키보드·기어·조명 연동) | 보임 | 숨김 |
| 3D 자동 시연 | 에뮬레이터 | 정차 중 허용 |
| `distractionOptimized` | 선언 | 없음 (주행 중 화면 제한) |
| R8 코드 최적화 | 없음 | **끔** (아래 참고) |
| 서명 | 디버그 키 | `release/carity-release.jks` (v2 서명) |
| 권한 (최종) | 개발 시험용 포함 | `INTERNET`, `CAR_SPEED`, `CAR_DRIVE`, `TTS_SERVICE`, Vehicle SDK 연결용 `VEHICLE_BINDING` |

- 위치 SDK 라이브러리가 자동으로 넣는 `FUSED_LOCATION_BINDING` 권한도 release 매니페스트에서 제거합니다. 남아 있으면 위치 사용 앱으로 보일 수 있습니다.
- **R8을 끈 이유**: 처음에는 `androidx`·`kotlin` 패키지만 최적화하는 설정(`optimization.packageScope`)이 켜져 있었습니다. 이 설정으로 만든 APK는 실행 직후 `IllegalAccessError: Class kotlin.collections.* ... is inaccessible`(AndroidX 시작 단계)로 꺼졌습니다. 최적화를 끈 뒤 정상 동작했고, APK는 19.1 MB → 26.7 MB가 됐습니다(제한 600 MB).
- 빌드 순서: `Carity.bat` 메뉴 11(서명 키, 처음 1회) → 12(제출용 APK, 에뮬레이터 설치 선택) → 13(스토어 스크린샷).

제출 절차와 콘솔 입력값 초안은 `release/제출_체크리스트.md`에 있습니다.

## 15. 부록 — 용어, 상수, 파일, 로그 태그

### 15-1. 용어

| 용어 | 뜻 |
|---|---|
| 간격(clearance) | 자차 차체(회전 반영)와 가장 가까운 장애물·벽 사이 거리 |
| 안쪽 모서리 | 장애물에서 자차 쪽 가장자리 |
| 경로상 객체 | 자차 진행 폭(±1.1 m)에 0.3 m 이상 걸친 객체 |
| 대향차 | 경로상에서 정지물체보다 뚜렷하게 빨리 커지는(다가오는) 차량 |
| 상황 키 | 같은 안내를 반복하지 않기 위한 판단 식별자 (행동 + 방향) |
| 고스트 차 | 튜토리얼에서 경로를 먼저 보여 주는 반투명 차 |
| SAT | 분리축 정리. 두 다각형이 겹치는지 판단하는 방법 |
| Alley Pass | 좁은 곳에서 사용자 확인 후 미러·창문·비상등을 순서대로 실행하는 가상 매크로 |

### 15-2. 주요 상수

| 상수 | 값 | 위치 |
|---|---|---|
| 근접(빨강) / 주의(주황) | 0.3 m / 0.8 m | `SideClearanceWarning`, `AlleyDecisionEngine.NEAR` |
| 핸들 조정 권고 | 0.6 m | `AlleyDecisionEngine.CAUTION` |
| 골목 권장 속도 | 10 km/h | `AlleyDecisionEngine.SLOW_KMH` |
| 매크로 조건 | 10 km/h 이하, 1.2 m 이내, 15초 안 브레이크 3회 | `AlleyMacroGate` |
| 경로 단면 간격 / 조향 기울기 | 0.5 m / 0.3 | `CorridorPlanner.STEP`, `MAX_SLOPE` |
| 장애물 여유 / 대향차 여유 / 목표 여유 | 0.25 / 0.3 / 0.35 m | `MARGIN`, `PASS_MARGIN`, `COMFORT` |
| 진행 폭 / 접근 구간 | ±1.1 m / 6 m | `LabelSceneBuilder.PATH_HALF`, `LEAD` |
| 라벨 신뢰도 / 잘린 박스 신뢰도 | 0.4 / 0.5 | `MIN_CONF`, `MIN_CONF_TRUNCATED` |
| 거리 검증 허용 오차 | 0.02 m | `LabelDistanceCheck.TOLERANCE` |
| AI 호출 지연 / 규칙 대체 대기 | 0.4초 / 3.5초 | `AlleyPassSimulationView.updateJudgement`, `TutorialActivity` |
| Qwen 응답 제한 | 45초 | `AiJudge.QWEN_TIMEOUT_MS` |
