# SDK 실제 제어 검증 — 2026-11-12

## 결론

자체 앱 버튼 → Pleos SDK set 요청 → 별도 get 재조회 → 원래값 복원 순서로 emulator-5554에서 시험했다.
Virtual Console을 직접 조작해 성공으로 판정한 것이 아니다.
사용자가 Console에서 정차를 설정했고, 앱에서도 매 쓰기 전 AAOS 속도 0.0 m/s 및 P단을 확인했다.

| 항목 | 실제 시험 | 결과 |
| --- | --- | --- |
| 사이드미러 열선 | 0 → 1 → 0 | 변경값 및 복원값 재조회 성공 |
| 앰비언트 스위치 | OFF → AUTOMATIC → OFF | 모드 변경 및 복원 재조회 성공. ON 모드 점등·화면상의 빛 변화는 미검증 |
| 조수석 창문 위치 | 0 → 1, 이후 0 → 10 요청 | 완료 콜백 수신. 반복 재조회는 0 유지. 요청값 적용 미확인 |
| 앰비언트 밝기 | 100 → 99, 이후 100 → 50 요청 | 권한 보완 후 완료 콜백 수신. 재조회는 100 유지. 적용 미확인 |

| 개별 조수석 도어 잠금 | ROW_1_RIGHT 조회 시도 | 장치에서 area ID 0x4 unsupported 오류. 쓰기 전 중단 |
| 조수석 도어 위치 | 0 → 1 요청 | 완료 콜백 수신, 재조회 0 유지. 적용 미확인 |
| 미러 폴딩 / 비상등 제어 | 확인한 공개 SDK에 쓰기 API 없음 | 임의 API 작성·호출하지 않음 |

완료 콜백만으로 실제 상태 변경 성공을 판정하면 안 된다는 것을 확인했다.
재조회가 유지된 원인이 장치 미구현, Console의 상태 덮어쓰기, 모드·잠금 조건, SDK/서비스 캐시 문제 중 무엇인지는 아직 분리하지 못했다.
따라서 해당 항목은 영구 미지원이라고 단정하지 않고 '현재 환경 적용 미확인'으로 표시한다.
실차의 물리적 액추에이터 동작이나 Console 화면에서의 시각적 변화는 이번 앱 로그 검증과 별개이다.

## 권한 관련 새 확인

Light.kt의 인터페이스와 KDoc는 일부 앰비언트 set 메서드에 CAR_LIGHTS를 명시하지만,
LightImpl.kt의 실제 setAmbientLightBrightness / setAmbientLightBrightnessColor /
setAmbientLightSwitch 구현은 CONTROL_CAR_LIGHTS를 요구한다.

- CAR_LIGHTS만 있을 때 실제 쓰기는 need Permission 오류.
- 디버그 Manifest에 CONTROL_CAR_LIGHTS 추가 후 오류 해소 및 완료 콜백 수신.
- 앱 설치 패키지에서 CONTROL_CAR_WINDOWS, CONTROL_CAR_LIGHTS, CONTROL_CAR_MIRRORS,
  CONTROL_CAR_DOORS 및 android.car.permission.CAR_POWERTRAIN의 granted=true 확인.
- 기존 SDK 정적 점검 문서의 권한 설명보다 이 런타임 결과와 구현부 확인을 우선한다.

## 남은 검증과 구현 판단

- 창문·도어·밝기·색상은 성공 기능으로 UI에 활성화하기 전에 상태 미반영 원인을 조사해야 한다.
- 앰비언트 시험 당시 스위치는 OFF였다. ON 모드에서 밝기·색상 적용이 달라지는지 아직 미검증.
- 창문 잠금, 장치 모드, Console의 지속 입력 여부도 후속 조사 후보이다.
- 앰비언트 스위치는 AUTOMATIC 모드만 시험했으므로 ON/OFF 점등 성공으로 확대 해석하지 않는다.
- 색상 비교는 RGB 24비트 기준이다. alpha 정규화와 별개로 RGB가 흰색을 유지해 빨강 적용 실패로 기록했다.
- 복원 로그는 원래값 재조회 확인을 뜻한다. 변경되지 않은 항목이 실제로 움직였다가 돌아왔다는 뜻은 아니다.
- 미러 열선은 폴딩을 대체하지 않으며 Alley Pass 핵심 제어 기능으로 억지로 포함하지 않는다.
- MVP는 실제 수신 상태와 안내 UI를 우선 구성하고, 제어 미확인 항목은 미확인·시뮬레이션으로 명시한다.
