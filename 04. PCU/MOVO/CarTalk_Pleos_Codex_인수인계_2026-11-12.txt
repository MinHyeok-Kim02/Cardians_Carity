CarTalk / MOVO - Pleos Connect 공모전 개발 인수인계 메모
정리 기준일: 2026년 11월 12일(목)
최종 제출 기한: 2026년 11월 15일(일)
용도: Android Studio에서 Codex에게 기존 대화와 개발 맥락을 전달하기 위한 텍스트

====================================================================
0. 가장 중요한 최신 결정 (반드시 우선 적용)
====================================================================
- 프로젝트는 현대자동차그룹 Pleos Connect / Pleos Playground 기반 차량용 Android 앱이다.
- 초보 운전자가 좁은 골목길, 주차장, 차량 교행 상황에서 안전하게 대응하도록 돕는 서비스다.
- 초안 기획서(MOVO_v1.md / 문서 내부 제목 CarTalk v3)에는 Ghost View/Ghost Line 기능이 있으나,
  팀 논의에서 "이미 있는 기능이고 차별성이 부족하다"는 이유로 구현에서 제외했다.
- 그러므로 Codex는 Ghost View, 미래 주행 궤적 오버레이, 복잡한 3D 궤적 렌더링을 구현 대상으로
  임의 포함하지 말 것. 디지털 트윈 기반 '정차 중 상황별 튜토리얼'의 유지 여부는 아직 확정되지 않았다.
- 사용자의 담당 기능은 "Alley Pass(좁은 골목길 교행 보조)"다.
- 마감까지 시간이 짧으므로 '동작하는 최소 기능(MVP)'을 우선한다.
- 실제 Pleos SDK로 되는 기능 / Virtual Console에서만 조작 가능한 기능 / 미확인 기능을 명확히 구분한다.

1. 전체 서비스 및 기존 기획서의 맥락
====================================================================
초기 프로젝트명: CarTalk(카톡). 업로드한 기획서 파일명은 MOVO_v1.md.
공모 분야: 안전 운전 & 모빌리티 라이프 케어.

아이디어의 핵심:
  1) 차량 정보 및 상태를 이용해 좁은 공간에서의 위험 상황을 인지한다.
  2) 화면의 기준선 및 앰비언트 라이트로 위험 방향을 직관적으로 표시한다.
  3) 운전 중에는 화면을 오래 보지 않도록 Zero-Look 음성 안내를 제공한다.
  4) 골목길 교행 시 안전한 대응을 안내하고, 지원 가능한 차량 기능을 사용자 요청에 따라 제어한다.
  5) 정차 중 상황별 학습/튜토리얼을 제공하는 아이디어가 있으나 최종 구현 범위는 재확인 필요.

기획서의 기존 6개 항목:
  - CarInfo 차량 정보 자동 인식
  - 빨간 기준선 및 앰비언트 라이트 동기화
  - Zero-Look 음성 코칭
  - Alley Pass (사이드미러/창문/비상등 관련 안내 및 제어)
  - 시뮬레이션/튜토리얼
  - Ghost View/궤적 시뮬레이션 (최신 팀 결정: 제외)

주의: 기획서에는 제어 가능한 것처럼 기술된 API와 실제 공개 SDK의 지원 범위가 다를 수 있다.
최신 팀 결정과 공식 SDK 확인 결과가 옛 기획서 문구보다 우선한다.

2. 사용자 담당: Alley Pass 정의
====================================================================
목표:
  좁은 골목에서 차량과 마주치거나 주변 공간이 좁을 때, 차량의 저속/정차 상태 및
  (가능하다면) 주변 장애물 정보를 바탕으로 운전자에게 필요한 조치를 안내한다.

초기 기획의 동작:
  - 저속, 브레이크 반복, 주변 차량/장애물 근접을 감지하여 Alley Pass 상황 인식
  - 사이드미러 접기, 조수석 창문 부분 개방, 비상등 점멸 등의 보조 기능
  - 음성으로 상태 및 조치를 안내

현재 권장 수정:
  - 주행 중 자동으로 사이드미러를 접는 기능은 후방 시야를 가리므로 실제 동작에서 제외한다.
  - 창문은 SDK 지원과 제어 권한 및 안전 조건이 확인된 경우에만, 정차 상태에서
    사용자의 명시적인 요청으로 조작한다.
  - 비상등 제어는 읽기/쓰기 API 지원을 따로 확인한다. 불가능하면 '모의 제어'로 분리한다.
  - 주변 차량과의 실제 거리 데이터가 없다면 '테스트용 가상 거리 입력'으로 위험 감지 UI를 시연하되,
    이를 실제 차량 센서 측정값이라고 표시하지 않는다.
  - 실제 조향 명령(예: 핸들을 무조건 180도 돌려라)이나 충돌을 보장해 피하는 안내는
    검증되지 않은 센서 정보로 제공하지 않는다. 정차 및 주변 확인을 우선 안내한다.

Alley Pass의 일요일 MVP 성공 기준:
  A) 앱에서 '좁은 골목길' 시나리오를 활성화할 수 있다.
  B) 차량의 저속/브레이크 상태를 SDK에서 읽어오면 반영한다(지원 안 되면 테스트 모드로 구분).
  C) 화면에 Alley Pass 안내 및 상태가 표시된다.
  D) 정차 상태에서 사용자가 버튼을 눌러 창문 위치 제어를 요청할 수 있다(지원·권한 확보 시).
  E) 제어 요청 후 실제 상태를 다시 읽어서 변경 여부를 확인한다.
  F) 지원되지 않는 사이드미러/비상등 기능은 '미지원' 또는 '시뮬레이션'으로 명확히 표시한다.

3. 개발 환경과 현재 확인된 사실
====================================================================
- Windows 노트북 + Android Studio를 사용 중이다.
- Android Studio에 Pleos Connect Emulator AVD가 설정되어 있고 실행에 성공했다.
- Running Devices 창 이름은 과거 스크린샷 기준 'Pleos test', AVD 표시는 Pleos Connect v2 / API 34다.
- Pleos Connect 기본 화면(Gleo/차량 화면)이 에뮬레이터에서 정상 구동된다.
- 별도의 웹 기반 Virtual Console을 사용하며, 과거 사용한 포워딩 명령은 아래와 같다.

    adb forward tcp:8088 tcp:8088

  브라우저 주소:

    http://127.0.0.1:8088/

- 사용자가 Virtual Console에서 확인한 조작:
  * 액셀러레이터(가속)
  * 브레이크
  * 조향각
  * 차량 속도/기어 관련 시뮬레이션
  * 창문
  * 앰비언트 라이트
  * 보닛 등 차량 바디 상태
- 제공한 스크린샷에는 Virtual Console의 주행 시각화, ACCEL/BRAKE/STEERING UI,
  창문 패널 및 앰비언트 조명이 보였다. Pleos Connect 기본 차량 화면도 보였다.
- 사용자 설명에 따르면 Virtual Console 조작이 Pleos 에뮬레이터의 기본 차량 UI에 반영된다.

[중요한 구분]
  1) Virtual Console <-> Pleos 기본 차량 화면 연동: 사용자 스크린샷/설명으로 확인됨.
  2) Virtual Console <-> 우리 팀이 작성한 Kotlin 앱의 SDK 데이터 수신: 아직 별도 검증되지 않음.
     기본 Pleos 화면의 속도가 변하는 것은 우리 앱이 속도 API를 읽는다는 증거는 아니다.
  3) Virtual Console에서 특정 기능을 조작할 수 있다는 사실만으로
     제3자 앱이 공식 SDK를 통해 같은 기능을 읽거나 쓸 수 있다는 뜻은 아니다.

- Virtual Console의 도로 시뮬레이션에는 다른 차량들이 보였지만,
  다른 차량과의 거리/측방 공간을 앱에 전달하는 API는 아직 확인되지 않았다.
- 거리 데이터가 없는 이유가 SDK 미설치 때문이라고 단정하지 않는다.
- 과거 Pleos SDK에서 FusedLocation 등 일부 기능은 준비 중인 것으로 보였으므로,
  현재 프로젝트 SDK/앱에서 지원되는 항목을 직접 확인할 것.
- 사용자는 Codex를 개발 환경에 연결해 둔 상태라고 밝혔다.
  그러나 이 ChatGPT 대화가 Codex 세션에 자동 공유되는 것은 아니다.

4. 검증해야 할 SDK/API 사항 (검증 전까지 단정 금지)
====================================================================
우선순위 상:
  [ ] 기존 Android 프로젝트가 정상 빌드되는가?
  [ ] 현재 프로젝트에 적용된 Pleos Vehicle SDK 버전은 무엇인가?
  [ ] Vehicle Service 초기화 및 연결이 되는가?
  [ ] 필요한 읽기/쓰기 Capability, 접근 권한은 제공되는가?
  [ ] 자체 앱에서 브레이크 상태를 실시간으로 읽을 수 있는가?
  [ ] 자체 앱에서 차량 속도를 읽을 수 있는가?
  [ ] 자체 앱에서 창문 위치를 읽고 변경 요청을 할 수 있는가?
  [ ] 변경 요청 후 조회 값이 실제 변경되는가?

우선순위 중:
  [ ] 조향각 조회 가능 여부
  [ ] 앰비언트 라이트 조회·제어 가능 여부
  [ ] 비상등 조회·제어 가능 여부
  [ ] 사이드미러 폴딩 제어 가능 여부
  [ ] 주변 차량/장애물 거리 또는 PDW 단계 API 존재 여부

과거 대화에서 언급된 클래스/함수(현재 프로젝트의 SDK 문서 및 자동완성으로 재확인 필요):
  - ai.pleos.playground.vehicle.api.*
  - CarInfo, Brake, SteeringWheel, Window, Light, SideMirror, Safety, TurnSignal
  - Window: checkWindowPositionCapabilities, getCurrentWindowPosition, setWindowPosition
  - AAOS: PERF_VEHICLE_SPEED (속도 데이터 후보, 권한/지원 확인)
  - Odometer는 주행 거리 관련이며 실시간 속도 자체와 구분할 것.
  - 앞선 대화에서는 Vehicle SDK 2.3.2라는 버전과 아래 의존성이 안내됨.
       implementation("ai.pleos.playground:Vehicle:2.3.2")
    단, 기존 프로젝트의 실제 버전/리포지토리/호환성을 먼저 확인하고 임의 변경하지 말 것.

과거 안내된 AndroidManifest 권한 이름(현재 SDK 공식 문서로 재확인):
  - pleos.car.permission.CAR_WINDOWS
  - pleos.car.permission.CONTROL_CAR_WINDOWS
  - pleos.car.permission.CAR_DRIVE
  모든 제어에는 적절한 권한과 차량 상태 확인이 필요하다.

주의 사항:
  - SideMirror 공개 설명에는 열선 위주의 기능이 확인되었고, 폴딩 API는 확인되지 않았다.
  - TurnSignal/Light에서 비상등 '쓰기' 가능 여부는 확인되지 않았다.
  - Window 위치값은 기기별 범위가 다를 수 있다. 예전 샘플의 0~10 같은 예시를
    곧바로 0~100% 또는 정확한 3cm로 해석하지 않는다.
  - 앰비언트 라이트의 #FF0000(빨강) 지원 여부는 확인되지 않았다.
    실제 지원하는 색상만 사용하고 화면 UI의 빨강 표시와 구분한다.
  - Safety라는 클래스가 있다고 해서 좌/우 장애물 거리(cm) 데이터가 제공되는 것은 아니다.

5. 권장 개발 구조
====================================================================
기존 프로젝트 파일을 먼저 확인하고 실제 구조에 맞춰 적용한다.
아래 이름은 제안일 뿐 기존 코드를 삭제하거나 무조건 새 프로젝트를 만드는 지침이 아니다.

  model/VehicleState.kt
    - speedKmh: Float?
    - brakePressed: Boolean?
    - steeringWheelDeg: Float?
    - leftClearanceM: Float?
    - rightClearanceM: Float?
    - isParked: Boolean?
    - source: PLEOS | SIMULATION

  data/VehicleDataSource.kt        공통 데이터 인터페이스
  data/PleosDataSource.kt          실제 Pleos SDK 데이터
  data/SimulationDataSource.kt     검증용/시연용 가상 데이터
  feature/alley/                  Alley Pass 화면/상태/제어 로직
  engine/AlleyPassEngine.kt        상황 판단 (규칙 기반)

원칙:
  - 동일한 UI/엔진이 실제 데이터 또는 가상 데이터를 받을 수 있도록 한다.
  - 각 값의 출처(PLEOS/SIMULATION)를 표시한다.
  - 수신 안 된 값을 임의의 안전한 수치로 대체하지 않는다(null/UNKNOWN 처리).
  - 차량 제어는 비동기 결과와 재조회 값을 함께 확인한다.
  - 주행 안전 조건이 확인되지 않으면 실제 제어를 실행하지 않는다.
  - 실제 API 시그니처는 SDK 문서/현재 의존성의 코드에서 확인하고 작성한다.

8. 우선 테스트 절차
====================================================================
1. Android Studio에서 현재 프로젝트를 열고 빌드/실행한다.
2. Pleos Connect AVD와 Virtual Console을 실행한다.
3. 자체 앱에서 브레이크 상태를 읽는 로그를 구현한다.
4. Virtual Console 브레이크를 조작하여 자체 앱의 Logcat 출력이 변하는지 확인한다.
5. 같은 방식으로 차량 속도 데이터 수신 여부를 확인한다.
6. Window API의 Capability와 읽기 권한/지원 범위를 조회한다.
7. 가능하면 P단/안전 정차 조건에서 '조수석 창문 테스트' 버튼을 구현한다.
8. 제어 요청 -> 완료/오류 확인 -> 창문 위치 재조회 -> 실제 변화 검증.
9. 장애물 거리 API가 없으면 개발자 전용 시뮬레이션 입력(예: 좌측 0.5m/우측 0.2m)을 쓴다.
